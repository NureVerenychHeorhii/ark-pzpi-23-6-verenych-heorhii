   2 ЗАВДАННЯ
Ключовою метою цієї практичної роботи є поглиблене вивчення
методологій написання «чистого коду» (Clean Code) та засвоєння технік
рефакторингу. У межах завдання студенту необхідно обрати інструментарій
(мову програмування), дослідити офіційні стайл-гайди (Style Guides) та кращі
практики (Best Practices), прийняті у професійній спільноті.
Як об'єкт дослідження було обрано мову системного програмування
Rust. Завдання полягає у тому, щоб на наочних прикладах продемонструвати
різницю між просто «робочим» та «ідіоматичним» кодом, обґрунтувати
необхідність дотримання конвенцій та проаналізувати програмні засоби, що
автоматизують контроль якості (Linters/Formatters). Результатом роботи є
оформлений звіт, що систематизує теоретичну базу та практичні навички.


3 ОПИС ВИКОНАНОЇ РОБОТИ
 3.1 Стандартизація коду в екосистемі Rust
Темою дослідження обрано стандарти оформлення коду мовою Rust. На
відміну від багатьох інших мов, де стиль може варіюватися від команди до
команди, Rust має суворо централізований підхід, описаний у RFC 430 («Rust
Style Guidelines»). Якщо філософія Perl звучить як «Є більше одного способу
зробити це», то філософія Rust — «Безпека та ясність понад усе». Компілятор
Rust (rustc) бере на себе роль суворого ментора, не дозволяючи писати код,
який може призвести до помилок пам'яті, а спільнота домовилася про єдиний
візуальний стиль, щоб унеможливити суперечки щодо форматування.
 3.2 Фундамент безпеки: Відмова від Unwrap
Аналіз розпочався з наріжного каменя надійності в Rust — обробки помилок.

На відміну від винятків (exceptions) в інших мовах, Rust використовує типи
Result та Option. Використання методу .unwrap(), що викликає аварійну зупинку
програми (паніку) у разі помилки, вважається поганим тоном у продакшн-коді.
Приклад:
// Поганий підхід (Non-idiomatic)
// Ризик "падіння" програми без пояснення причин
fn read_config() -> String {
std::fs::read_to_string("config.toml").unwrap()
}
// Хороший підхід (Idiomatic)
// Явна обробка можливих сценаріїв через Pattern Matching
fn read_config_safe() -> Result<String, std::io::Error> {
let content = std::fs::read_to_string("config.toml") ?;
Ok(content)

 3.3 Візуальне оформлення: Відступи та структура
Було вивчено вимоги до форматування. Загальноприйнятим стандартом
є використання 4 пробілів для відступу. Табуляція не використовується. Для
розстановки фігурних дужок застосовується так званий «1TBS» (One True
Brace Style): відкриваюча дужка знаходиться на тому ж рядку, що й
оголошення функції або оператора, і відокремлюється одним пробілом. Це
забезпечує компактність коду по вертикалі.
Приклад:
// Рекомендований стиль
fn calculate_metric(value: i32) {
if value > 100 {
process_high_load();
} else
{
process_normal();
}
}
 3.4 Правила іменування (Naming Conventions)
У Rust дотримання правил іменування контролюється на рівні попереджень
компілятора. Порушення цих правил робить код «чужорідним» для інших
розробників.
snake_case (маленькі літери через підкреслення) — використовується для
змінних, імен функцій та модулів.
UpperCamelCase (або PascalCase) — обов'язковий для типів користувача
(struct, enum) та трейтів.
SCREAMING_SNAKE_CASE — застосовується виключно для глобальних
констант та статичних змінних.
Приклад:
// Змінні та функції
let request_timeout = 30;
fn fetch_data_url() { ... }
// Структури та перелічення
struct UserProfile { ... }
enum ConnectionState { ... }
// Константи
const MAX_BUFFER_SIZE: usize = 1024;

 3.5 Лаконічність виразів: Неявне повернення
Було розглянуто особливість Rust як мови, орієнтованої на вирази
(expression-based). Використання ключового слова return наприкінці функції
вважається надлишковим «шумом». Якщо рядок не закінчується крапкою з
комою, його результат автоматично повертається з блоку.
Приклад:
// Надлишковий стиль (C-style)
fn multiply(a: i32, b: i32) -> i32 {
return a * b;
}
// Ідіоматичний стиль Rust
fn multiply(a: i32, b: i32) -> i32 {
a * b // Відсутність ";" сигналізує про повернення значення
}
 3.6 Функціональний підхід: Ітератори
Замість імперативних циклів for з мутабельними змінними-лічильниками,
Rust заохочує використання ланцюжків ітераторів. Це підвищує читабельність
(декларативність) і часто дає приріст продуктивності завдяки оптимізаціям
компілятора (Zero-Cost Abstractions).
Приклад:
let nums = vec![1, 2, 3, 4];
// Імперативний підхід (складніше читати)
let mut results = Vec::new();
for x in nums {
if x % 2 == 0 {
results.push(x * 2);
}
}
// Функціональний підхід (зрозумілий пайплайн)
let results: Vec < i32 > = nums.into_iter()
.filter(| x | x % 2 == 0)
.map(| x | x * 2)
.collect();
 3.7 Управління пам'яттю: Запозичення (Borrowing)
Найважливішим аспектом якості коду в Rust є грамотна робота з володінням
(ownership). Передача складних об'єктів за значенням може призвести до

зайвих алокацій пам'яті. Рекомендовано використовувати посилання
(слайси/зрізи), де це можливо.
Приклад:
// Неефективно: клонування рядка при виклику
using System.Xml.Linq;
fn print_greeting(name: String) { ... }
// Ефективно: використання рядкового слайсу (посилання)
fn print_greeting(name: &str) { ... }
 3.8 Документування коду (Rustdoc)
Розглянуто стандарт вбудованої документації. Коментарі, що
починаються з ///, підтримують розмітку Markdown. Хорошим тоном
вважається наявність секцій # Examples (приклади використання) та #
Panics (опис умов, за яких функція може викликати збій).
Приклад:
/// Обчислює факторіал числа.
///
/// # Examples
/// ```
/// let n = factorial(5);
/// ```
pub fn factorial(n: u32) -> u32 { ... }
 3.9 Інструментарій якості: Cargo Fmt та Clippy
Проведено огляд інструментів екосистеми:
- Rustfmt — форматувальник коду. Він усуває необхідність сперечатися
про стиль на Code Review, автоматично приводячи весь проект до
єдиного вигляду за командою cargo fmt.
- Clippy — просунутий лінтер. Він містить сотні правил і підказує, як
зробити код не просто робочим, а швидшим та ідіоматичним (наприклад,
запропонує замінити ручний розрахунок довжини ітератора на метод
.count()).

3.10 Висновки до розділу
Дослідження показало, що Rust вимагає високої дисципліни, проте надає
потужні інструменти для її підтримки. Дотримання принципів «The Rust Way»

(безпека типів, імутабельність за замовчуванням, використання ітераторів)
дозволяє мінімізувати технічний борг ще на етапі написання коду.


   4 ВИСНОВКИ
У ході виконання практичної роботи було детально вивчено принципи
оформлення та структурування програмного коду мовою Rust. Основою
аналізу слугували офіційні гайдлайни (RFC 430) та рекомендації спільноти.
Було встановлено, що сувора типізація та вимоги компілятора Rust
безпосередньо впливають на чистоту коду. Застосування ідіоматичних
конструкцій, таких як match для обробки помилок замість unwrap,
використання незмінних змінних за замовчуванням та функціональних
ланцюжків ітераторів, робить код передбачуваним та безпечним.
Окрему увагу було приділено автоматизації процесів перевірки якості.
Використання вбудованих інструментів cargo fmt та cargo clippy дозволяє
розробнику зосередитися на бізнес-логіці, делегуючи рутинну перевірку
стилю та пошук потенційних вразливостей автоматиці. Таким чином,
дотримання стандартів у Rust — це не просто питання естетики, а гарантія
надійності та продуктивності програмного продукту.
