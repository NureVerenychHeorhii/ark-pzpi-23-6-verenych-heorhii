2	ЗАВДАННЯ

Головною метою цієї роботи є практичне засвоєння принципів "чистого коду", вміння знаходити проблемні місця ("запахи коду") та виправляти їх, змінюючи внутрішню архітектуру програми без впливу на її функціонал.
В рамках завдання необхідно обрати три техніки рефакторингу (базуючись на класичній праці Мартіна Фаулера або специфіці мови C++) та застосувати їх до реальних прикладів коду. Студент має надати фрагменти коду у стані "До" та "Після" оптимізації, а також аргументувати, чому саме ці зміни позитивно впливають на якість програмного продукту, його швидкодію чи зручність супроводу.
Для реалізації завдання було обрано такі методи:
-	Extract Method (Відокремлення методу);
-	Replace Magic Number with Symbolic Constant (Заміна магічного числа на іменовану константу);
-	Decompose Conditional (Декомпозиція умовних операторів).








3	ОПИС ВИКОНАНОЇ РОБОТИ

3.1	Вступ: Роль рефакторингу в розробці на C++

Даний звіт присвячено темі покращення якості коду засобами рефакторингу в контексті мови C++. Оскільки C++ є мовою зі складною синтаксичною структурою та прямим керуванням ресурсами, код на ній має тенденцію швидко ставати заплутаним та важким для читання. Регулярний рефакторинг дозволяє тримати проект у "здоровому" стані, спрощує навігацію по файлах та зменшує ризик виникнення помилок при додаванні нових функцій.
3.2	Метод 1: Extract Method (Відокремлення методу)

Суть проблеми: Одним із найпоширеніших недоліків коду є наявність так званих "God Methods" або просто занадто довгих функцій. Коли один метод відповідає і за логіку обчислень, і за виведення даних, і за підготовку змінних, його стає неможливо читати. Втрачається контекст, а будь-яка спроба змінити частину логіки може зламати суміжні процеси. Також такий код порушує принцип єдиної відповідальності (SRP).

Код до рефакторингу: Розглянемо функцію PrintOwing, яка перевантажена обов'язками: вона і малює інтерфейс (банер), і виконує математичні розрахунки боргу, і виводить кінцевий результат.

void PrintOwing(double amount)
{
    // Виведення декоративного заголовка
    std::cout << "**************************" << std::endl;
    std::cout << "***** Customer Owes ******" << std::endl;
    std::cout << "**************************" << std::endl;

    // Блок розрахунку заборгованості
    double outstanding = 0.0;
    for (int i = 0; i < 5; ++i)
    {
        outstanding += amount * 1.2; // імітація складної формули
    }

    // Виведення результату
    std::cout << "name: " << _name << std::endl;
    std::cout << "amount: " << outstanding << std::endl;
} 

Реалізація методу: Ми структурували код, винісши логічно завершені операції (друк заголовка, розрахунок, друк звіту) в окремі приватні функції. Основний метод тепер виступає у ролі диспетчера, який просто викликає підпрограми у правильному порядку.
Код після рефакторингу:

using System.Xml.Linq;

void PrintOwing(double amount)
{
    PrintBanner();
    double outstanding = CalculateOutstanding(amount);
    PrintDetails(outstanding);
}

void PrintBanner()
{
    std::cout << "**************************" << std::endl;
    std::cout << "***** Customer Owes ******" << std::endl;
    std::cout << "**************************" << std::endl;
}

void PrintDetails(double outstanding)
{
    std::cout << "name: " << _name << std::endl;
    std::cout << "amount: " << outstanding << std::endl;
}

double CalculateOutstanding(double amount)
{
    double result = 0.0;
    for (int i = 0; i < 5; ++i)
    {
        result += amount * 1.2;
    }
    return result;
}

Переваги:
-	Садокументованість: Назви нових методів чітко кажуть, що вони роблять. Немає потреби в коментарях.
-	Повторне використання: Метод PrintBanner тепер можна викликати з інших частин програми.
-	Зручність налагодження: Помилку в розрахунках тепер легше локалізувати саме в CalculateOutstanding.


3.3	Метод 2: Replace Magic Number with Symbolic Constant 

Суть проблеми: Зустрічаючи в коді числа на кшталт 9.81, 3.14 або 120, інший програміст (або ви самі через місяць) може не зрозуміти їхнього походження та призначення. Це так звані "магічні числа". Вони небезпечні тим, що при необхідності змінити значення доведеться шукати всі його входження по всьому проекту, що часто призводить до помилок.
Код до рефакторингу: Функції для фізичних розрахунків та перевірки безпеки руху, де використовуються "жорсткі" літерали без пояснень.

double CalculatePotentialEnergy(double mass, double height)
{
    // 9.81 - неясно, чи це константа g, чи інший коефіцієнт
    return mass * 9.81 * height;
}

bool IsSpeedSafe(double speed)
{
    // 120 - виглядає як випадкове обмеження
    if (speed > 120)
    {
        return false;
    }
    return true;
 
Реалізація методу: Всі незрозумілі числа було замінено на константи з ключовим словом const (або constexpr для C++11 і вище). Назви констант написані у верхньому регістрі, що є стандартом для таких змінних, і повністю описують суть значення.
Код після рефакторингу:

// Константи винесено в глобальну область або конфігураційний файл
const double GRAVITATIONAL_ACCELERATION = 9.81;
const double MAX_SAFE_SPEED_KMH = 120.0;

double CalculatePotentialEnergy(double mass, double height)
{
    return mass * GRAVITATIONAL_ACCELERATION * height;
}

bool IsSpeedSafe(double speed)
{
    if (speed > MAX_SAFE_SPEED_KMH)
    {
        return false;
    }
    return true;

 
Переваги:
-	Ясність намірів: GRAVITATIONAL_ACCELERATION не залишає питань щодо природи числа.
-	Централізоване керування: Зміна значення константи відбувається в одному рядку, і це автоматично оновлює логіку всієї програми.
-	Зменшення помилок: Виключається ризик випадкового введення 9.80 замість 9.81 в одному з місць використання.
3.4	Метод 3: Decompose Conditional

Суть проблеми: Складні бізнес-правила часто породжують громіздкі конструкції if-else. Коли умова містить багато логічних операторів (&&, ||), а тіло блоку займає десятки рядків, стає вкрай важко зрозуміти логіку виконання програми. Це змушує розробника витрачати зайвий час на аналіз коду.
Код до рефакторингу: Метод розрахунку ціни квитка, де перевірка сезону ("чи це літо?") реалізована через пряме порівняння дат всередині if.

using static System.Runtime.InteropServices.JavaScript.JSType;

double CalculateTicketPrice(Date date, int quantity)
{
    double price;
    // Важко читаєма умова з перевірками меж дат
    if (date.Before(Date(date.Year, 6, 1)) || date.After(Date(date.Year, 8, 31)))
    {
        price = quantity * _winterRate + _winterServiceCharge;
    }
    else
    {
        price = quantity * _summerRate;
    }
    return price;
}
 
Реалізація методу: Складну умову було інкапсульовано в окремий метод з булевим значенням повернення IsSummer(). Дії, що виконуються в гілках if та else, також винесено у відповідні методи з промовистими назвами.
Код після рефакторингу:

using static System.Runtime.InteropServices.JavaScript.JSType;

double CalculateTicketPrice(Date date, int quantity)
{
    if (IsSummer(date))
    {
        return SummerCharge(quantity);
    }
    else
    {
        return WinterCharge(quantity);
    }
}

bool IsSummer(const Date& date)
{
    return date.After(Date(date.Year, 5, 31)) && date.Before(Date(date.Year, 9, 1));
}

double SummerCharge(int quantity)
{
    return quantity * _summerRate;
}

double WinterCharge(int quantity)
{
    return quantity * _winterRate + _winterServiceCharge;
}

Переваги:
-	Виразність: Головний метод читається як природна мова: "Якщо літо — літній тариф, інакше — зимовий".
-	Абстракція: Деталі реалізації перевірки дати приховані. Це дозволяє змінювати межі сезонів, не чіпаючи основну логіку розрахунку ціни.
-	Спрощення: Зменшено рівень вкладеності та когнітивне навантаження при читанні коду.




4	ВИСНОВКИ

Під час виконання лабораторної роботи було проведено аналіз та рефакторинг коду на мові C++ із застосуванням трьох різних підходів. Техніка Extract Method дозволила перетворити монолітні процедури на набір зрозумілих кроків, значно покращивши структуру програми. Метод Replace Magic Number продемонстрував важливість іменування констант для забезпечення ясності коду та безпеки його подальшої модифікації. Підхід Decompose Conditional довів свою ефективність у спрощенні складної логіки розгалужень, зробивши код більш декларативним. 
Отже, застосування цих методів не лише покращує візуальне сприйняття коду, але й робить його більш стійким до змін та зручним для командної розробки.
